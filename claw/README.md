# Claw · 认知路由

一个把**「教学决策」拆成四层**的 Agent 系统。

不是"你问我答"，而是：**先看你卡在哪、卡成什么样，再决定怎么教**。

```
用户一句话 → 四路并行观察 → 认知侦察 → 带工具执行 → 逐步推给前端
```

3,162 行 Python，42 个文件，从 LLM 客户端到 WebSocket 推送全部自己写，不依赖 LangChain / LlamaIndex。

---

## 为什么不是普通对话 Agent

普通对话 Agent 的链路是：`输入 → 检索 → 生成`。

这条链路默认了"用户说的是他真正的问题"。但教学场景里最常见的失败是——**用户说"我懂了"，其实卡在前置概念上**；或者"我听不懂"，其实是上一轮讲的方式不对。

Claw 把这一步显式拆出来：

| 层次 | 干什么 | 为什么必须单独一层 |
|---|---|---|
| **L1 观察** | 四路并行：情绪指纹 / 断点诊断 / 优势识别 / 知识流 | 四件事互不依赖、输入相同 → 可以并发；串行跑就是 4 倍延迟 |
| **L2 侦察** | 把四路结果合成"这一轮该怎么教" | 字段之间会**互相矛盾**（情绪说急躁、断点说概念缺失、优势说前置已掌握）——需要一层专门读矛盾，不能硬编码 if-else |
| **L3 执行** | ReAct 循环 + 工具调用，生成教学回复 | 需要外部信息（检索/读画像）才能答，属于"边想边查" |
| **L4 接入** | FastAPI + WebSocket，把过程逐步推给前端 | 一次响应要 5~10 秒，全等完再返回体验极差 |

## 四层架构

```
                    ┌──────────── L1 观察层（asyncio.gather 四路并发）────────────┐
用户输入 ──────────→ │ Agent1 情绪指纹   Agent2a 断点诊断                          │
                    │ Agent2b 优势识别  Agent2c 知识流                            │
                    └──────────────────────────┬──────────────────────────────────┘
                                               ↓ 三份 JSON
                    ┌──────────── L2 侦察层 ────────────────────────────────────┐
                    │ Agent2.5：读字段之间的张力，输出"这一轮怎么教"              │
                    └──────────────────────────┬──────────────────────────────────┘
                                               ↓ 教学指导
                    ┌──────────── L3 执行层 ────────────────────────────────────┐
                    │ Agent3：ReAct 循环（Thought → Action → Observation）        │
                    │ 工具：tavily_search / read_plan    最多 3 轮，用完强制收尾   │
                    └──────────────────────────┬──────────────────────────────────┘
                                               ↓ 流式片段
                    ┌──────────── L4 接入层 ────────────────────────────────────┐
                    │ FastAPI：7 个 REST 端点 + /ws 逐步推送 + 静态页            │
                    └───────────────────────────────────────────────────────────┘
```

### L1 为什么能并发：三条判据

拆分之前先判断能不能拆，三条都满足才拆：

| 判据 | 检验 |
|---|---|
| **正交** | 四个 Agent 关注的东西不重叠（情绪 / 断点 / 优势 / 知识流） |
| **同输入** | 都只吃「本轮输入 + 技能文件 + 历史上下文」，不需要彼此的结果 |
| **无依赖** | 没有任何一个的输出是另一个的输入 |

三条全部满足 → `asyncio.gather` 一次发四个请求，总耗时 = **最慢的那一路**，不是四路之和。

> 反例：如果先诊断断点、再根据断点决定要不要看知识流，那就只能串行——**并发的前提是"没有先后关系"，不是"想快就能快"**。

### L2 为什么必须存在

L2 的输入是三份结构化的分析结果，输出是一段教学指导。它的价值不在"多一层"，而在**它允许输入互相矛盾**：

- 情绪层说：急躁、连续两轮不满意
- 断点层说：卡在"前置概念缺失"
- 优势层说：前置概念**其实已掌握**（用户能正确复述）

同一份数据里出现"该补前置"和"前置已会"两个结论时，**没有任何 if-else 能穷举这种组合**。所以交给一层专门做判断，并且要求：**每个推断必须带证据**。

### L3 ReAct：熔断比循环更重要

```
while rounds < 3:
    LLM 输出 → 有 tool_call? → 执行 → 结果塞回 messages → 下一轮
                           → 无 tool_call → 直接返回
第 3 轮结束强制 tools=None，逼模型用已有信息收尾
```

`max_rounds` 和"最后一轮禁用工具"两件事缺一不可：只有轮数上限，模型可能在最后一轮还要工具，直接崩；只有禁用工具，没有上限，可能无限查。

### L4 为什么要 WebSocket

一次完整响应 5~10 秒。如果等全部结束再返回一个 JSON，用户面对的是 10 秒白屏。
改成 `WS` 之后每一层出结果就推一段：**先出情绪判断，再出诊断，再出教学**。用户感知到的延迟从 10 秒变成 1 秒。

## 四个工程细节

### 1. 上下文分层：靠数据本身判断，不靠外部计数器

多轮对话要记住"上一轮教过什么"。做法不是维护一个 `round_id` 变量，而是看**最后一条记录是否完整**：

```python
def _current_round(records):
    if records and "guidance" not in records[-1]:
        return records[-1]      # 上一轮还没写完 → 续填
    return 新建一轮()            # 上一轮已完整 → 开新的一层
```

一条记录的结构是 `{round_id, timestamp, emotion, breakpoint, guidance}`。三个 Agent 依次写入，`guidance` 是最后一步——**它出现了，就代表这一轮走完了**。

好处：进程重启、并发写入都不会错乱，状态完全由数据表达。

### 2. LLM 客户端：六级降级 + 发请求前先算账

外部 LLM 有六种失败方式，每一种都要有明确行为，不能一挂就整个链路停：

| 失败 | 处理 |
|---|---|
| HTTP 500 | 指数退避重试 |
| HTTP 401 | 不重试（重试一万次也一样），直接报配置错误 |
| HTTP 429 | 退避重试 |
| 非 200 状态 | 记录状态码与响应片段 |
| 返回体不是合法 JSON | 进解析兜底，保留 raw 输出 |
| `choices` 为空 | 返回结构化错误，不抛异常 |

**token 预检**：发请求之前先估算输入 token，超过模型上限就直接拒绝并说明——**不花一次网络往返去换一个 400**。

### 3. CPU 密集不能进事件循环

embedding 计算是纯 CPU 的同步阻塞调用。放在 `async def` 里会把整个事件循环**卡死**（期间所有协程停摆）。

```python
await asyncio.to_thread(同步的embedding函数, 参数)   # 扔到线程池
```

这是 FastAPI / asyncio 最常见的性能事故：**函数是 `async` 的，不代表里面的代码不阻塞**。

### 4. 工具注册表：加工具不改调度

```python
TOOL_REGISTRY = {}

def register_tool(name=None):
    def deco(func):
        TOOL_REGISTRY[name or func.__name__] = func
        return func
    return deco

@register_tool("tavily_search")
def tavily_search(query): ...
```

新增工具 = 写一个函数 + 加一个装饰器。ReAct 循环、schema 生成、调度逻辑一行都不用改。

## 实测数据

| 指标 | 优化前 | 优化后 |
|---|---|---|
| Agent2.5 单层耗时 | 22.9 ~ 99.6 s（波动极大） | **5.2 s** |
| Agent2.5 输入 token | 2,758 ~ 5,413 | **216（-96%）** |
| 技能提示词 | 280 行 | **90 行** |
| L1 四路总耗时 | 四路串行相加 | **= 最慢一路** |

耗时波动 4 倍的原因不是模型不稳定，是提示词里塞了太多"可选分支"，模型每次挑不同的路径。**把提示词从 280 行压到 90 行，耗时和 token 一起降下来了**——这是这个项目里收益最高的一次改动。

## 运行

```bash
# 从仓库根执行（claw 是包，必须用 -m 运行）
pip install fastapi uvicorn httpx python-dotenv faiss-cpu pymupdf numpy requests sentence-transformers tiktoken

copy claw\.env.example claw\.env    # 填两个 key
```

`.env` 只有两项：

| 变量 | 用途 |
|---|---|
| `Deepseek_key` | 所有 Agent 的 LLM 调用 |
| `TAVILY_API_KEY` | Agent3 的联网检索工具 |

```bash
python -m claw.main              # CLI 版：终端里对话，逐层打印
python -m claw.server.main       # Web 版：FastAPI + WebSocket，浏览器打开 127.0.0.1:8080
```

> ⚠️ **不能 `python claw/main.py`**。代码里用的是 `from claw.Agent1...` 这种包内绝对导入，只有从仓库根用 `-m` 启动才能解析。

## 目录

```
claw/
├── Agent1/        情绪指纹：情绪类型 + 强度 + 触发词 + 趋势
├── Agent2/        断点诊断 + 优势识别 + 知识流（三个技能文件驱动同一层）
├── Agent2_5/      认知侦察：读四路结果的矛盾，输出教学指导
├── Agent3/        教学执行：ReAct 循环 + 工具注册表
├── shared/        共享层：LLM 客户端 / 轮次存储 / 向量检索 / 画像
├── server/        FastAPI：7 REST + WebSocket + 静态页
├── portrait/      学习者画像：长期偏好与卡壳模式
├── onboarding/    首次使用引导
├── main.py        CLI 主链路（四路 gather + 串行决策）
└── __main__.py    包入口
```

## 已知限制

- 没有单元测试，验证靠手工跑链路（这是本项目最大的工程缺口）
- LLM 调用没有做并发限流，四路并发在低配额 key 上容易触发 429
- 画像系统只做读写，没有做画像更新的置信度衰减
