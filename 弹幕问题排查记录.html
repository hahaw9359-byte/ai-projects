弹幕收不到 —— 完整排查记录

日期：2026-10-12 ｜ 时间跨度：12:10 ~ 14:40（约 2.5 小时） 最终结果：两个根因全部修复，弹幕完全正常（实测：25 分钟收到 13 条真实弹幕）

一、问题现象

能不能连上？能。 程序每次都显示"已连上 B站房间 ✓"，心跳也正常。

能收到弹幕吗？收不到（或极少）。

现象随时间变化（这是最迷惑人的地方）：

阶段 时间 现象
① 时好时坏 12:20 前后 偶尔能收到一条，多数收不到 —— "几十条里抓一条"
② 完全收不到 13:00 之后 连接成功、心跳正常、弹幕一条都没有

关键证据（来自弹幕日志文件）：

14:08:17 已连上 ✓（节点 broadcastlv.chat.bilibili.com）
14:09:18 [报账] 数据包 2 ｜ 无用户消息     ← 60 秒只有 2 个包！
14:10:18 [报账] 数据包 2 ｜ 无用户消息

每分钟 2 个数据包 = 只有心跳回应。一个正常连接即使没人发弹幕， 也会收到榜单、进房、看播数等广播 —— 每分钟 2 个包，说明服务器几乎不推任何东西。

二、排查过程（完整时间线，含走过的弯路）

12:20 怀疑"过滤器太严"

  • 动作：放宽筛选（限流 5→12→20 条/10 秒、去重 30→10 秒、长度上限 40→60 字）
  • 结果：❌ 没解决问题（但不是白做 —— 筛选确实太严，这个修改保留了下来）

12:45 抓包实测 → 抓到第一个真凶：连接每 40 秒断一次

  • 动作：直接连进房间抓 80 秒原始流
  • 发现： [弹幕] 连接断了（keepalive ping timeout），3 秒后重连
  • 根因：websockets 库自带的 ping/pong 保活 —— B站服务器不回 pong， 库等 20 秒以为连接死了，自己掐断 → 约每 40 秒断一次，每次重连有 ~3 秒空窗，空窗期弹幕全丢
  • 修复：关掉库的 ping（ping_interval=None）+ 改用两样保活： 协议级心跳（每 30 秒）+ 沉默看门狗（90 秒无数据才重连）
  • 验证：✅ 110 秒长连接测试零断开（修复前 40 秒断一次）

12:45 顺手修了 2 个"崩溃单点"

  • 发现：LLM 或 TTS 任何一处报错，异常会冒泡带走整个后台线程 —— 此后所有弹幕都没人处理，而且画面还在动，完全看不出来
  • 修复：两处都改成"打一行提示、跳过继续"
  • 验证：✅ 故意注入报错测试 → 流水线存活

13:00 先做"可观测性"（关键一步）

  • 动作：加了三个诊断工具： 1. [抓到] 打印 —— 每条弹幕在进入过滤之前就打一行（判断"抓没抓到"） 2. 60 秒报账 —— 每分钟自动打印：数据包几个、各类消息几条、有没有不认识的消息 3. 文件日志 —— 所有关键事件写进 弹幕日志.txt（终端会滚动，文件不会）
  • 结果：✅ 从这之后"到底发生了什么"变得可见（后来的定位全靠它）

13:15 抓包实锤"能收到"（但只是偶尔）

  • 用同一套代码独立监听，收到了 1 条真实弹幕（"你用小脑的代码去抓"）
  • 判断：代码链路是通的，问题在别处

13:24 发现"聚合事件"（有效补充，但不是根因）

  • 监听抓到 DM_INTERACTION 消息 —— B站新版把重复弹幕/点赞/礼物打包成"聚合事件"下发
  • 补充解析：type 102（弹幕聚合）/ 104（礼物）/ 106（点赞）
  • 结果：✅ 这类消息不再漏（保留），但弹幕主流量还是收不到

13:52 怀疑协议版本（protover 2 vs 3）

  • 动作：A/B 对照实验（同一个大房间，两种协议版本各连 60 秒）
  • 结果：❌ 都是 0 条弹幕 → 不是这个原因（改动回滚）

14:15 大房间对照实验（排除了"他的房间有问题"）

  • 动作：连一个 73 万人在线的大直播间，68 秒
  • 结果：收到 21 个包 —— 有"进房、榜单"这类广播，但弹幕/礼物/点赞 0 条
  • 关键判断：连大房间都收不到弹幕 → 问题在我们自己身上，且是"弹幕类被单独屏蔽"

14:20 排除端口问题

  • 查 B站返回的服务器配置：wss_port = 443 → 我们连的端口是对的 ❌ 不是原因

14:25 排除"多连接"干扰

  • 把所有多余的监听连接全部杀掉（同一 IP 多条连接可能被服务器分流）
  • 结果：改善有限 —— 但仍保留这个原则（排查时只用一条连接）

14:30 对照 blivedm 源码 → 找到两个根因！ 🎯

  • 动作：把最成熟的 B站弹幕开源库（blivedm）的连接代码逐行读了一遍
  • 对照发现两处关键差异（我们都没有做）：
差异 blivedm（能收到） 我们（收不到）
设备指纹 buvid 连接前主动获取并放进认证包 空字符串
真实房间号 先解析短号（如房间 6 → 7734200）再认证 直接用 URL 上的号
  • 逐个实验验证：
  • 实验 E（加上 buvid）：收到第 1 条弹幕（突破！）
  • 实验 F（加上 buvid + 短号解析）：弹幕如潮水（房间 6，2400 万在线，几十条/分钟）

三、两个根因（最终答案）

根因 ①：认证包缺少设备指纹（buvid）

B站服务器的规则（实测出来的）：

连接带没带设备指纹 服务器行为
没带（空字符串） 让你连上、回你心跳、推进房/榜单基础广播 —— 但 弹幕、礼物、点赞一条不推
带了（真实 buvid3） 全部正常推送

我们的程序之前"礼貌地"连上了，但服务器把弹幕全屏蔽了。 这就是"能连上，但日志里啥也没有"的完整答案。

根因 ②：房间号必须用"真实号"

直播间 URL 里的号可能是短号（比如 live.bilibili.com/6 的真实房间号是 7734200）。

  • 获取 token 和认证包都只认真实号
  • 用短号认证 = 连接能建立，但广播对不上

四、修复操作（具体做了什么）

所有改动集中在 cerebellum/sources.py（弹幕源），共三处：

操作 1：新增"拿设备指纹"函数

async def _拿buvid(self) -> str:
    """去 B站接口拿一份 buvid3（设备指纹）"""
    async with httpx.AsyncClient(timeout=10) as c:
        r = await c.get("https://api.bilibili.com/x/frontend/finger/spi", ...)
        return r.json()["data"]["b_3"]

操作 2：连接前先解析"真实房间号"

# 短号 → 真实号（如 房间6 → 7734200）
r0 = await c.get("https://api.live.bilibili.com/room/v1/Room/room_init",
                 params={"id": self.room_id})
self.真实房间号 = r0.json()["data"]["room_id"]

操作 3：认证包换上新值

# 改前（收不到）
认证 = {"uid": 0, "roomid": self.room_id, "protover": 2,
        "buvid": "", "platform": "web", "type": 2, "key": token}

# 改后（正常）
认证 = {"uid": 0, "roomid": self.真实房间号, "protover": 3,
        "buvid": buvid, "platform": "web", "type": 2, "key": token}

六、这次踩的坑，总结成 5 条经验

  1. "能连上但收不到消息" → 第一件事是对照一个"确定能工作"的开源实现 （今天在 protover / 端口 / 账号风控 / IP 限流上绕了 3 小时 —— 全是错方向， 读 blivedm 源码 10 分钟就找到了真正的差异）

  2. 可观测性优先：文件日志比终端滚动可靠 —— "抓没抓到"要让证据说话，不靠猜

  3. 分层定位：网络层（连没连上）→ 解析层（消息认不认得）→ 过滤层 → 业务层， 每层都有独立的证据，一层层排除

  4. 单变量实验：一次只改一个东西（比如 protover 的 A/B 对照）， 否则改完有效果也不知道是哪个改动起的作用

  5. 别急着怪"平台风控" —— 但也不是不能怀疑平台， 关键是每一步都要拿到证据（比如"两条独立连接都收不到"这个证据， 才让'账号被限'的怀疑站不住脚）
