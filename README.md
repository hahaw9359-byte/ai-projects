# AI 虚拟主播 · 三脑项目

B 站直播间里一个真人主播的替身：**听弹幕 → 自己决定说不说 → 开口说话 → 嘴型跟着字走、表情跟着情绪变**。
Python 单机跑通全链路，不依赖任何云直播平台：

```
弹幕长连接 → 过滤/攒批 → LLM 决策 → 流式 TTS → 字级时间戳 → 60fps Live2D 渲染
```

观众发一句「有货吗」，从收到到开口大约 3 秒，中间经过五层。

---

## 它解决的真问题

直播是"话赶话"的场景，不是聊天框。这三个问题不解决，东西就跑不起来：

| 问题 | 现象 | 做法 |
|---|---|---|
| **两个脑抢同一张嘴** | 卖货讲到一半被弹幕打断，或者弹幕回应被卖货挤掉 | 抢画面 + 交还（`interrupt / resume`），队列按来源分级：**"卖货"过时可丢，"回应"一句不丢** |
| **说话有断档** | 一句说完才去合成下一句，句间空 1.78 秒，听着像掉线 | TTS 拆成**合成工人 + 播放工人**两段流水线，边播边合成 → 空档 **≈0，4 句省 5.4 秒** |
| **弹幕"能连上但一条不收"** | 认证包少一个设备指纹，服务器只推榜单不推弹幕 | 补齐 `buvid` + 用 `room_init` 解析真实房间号（短号不认） |

## 三个能深聊的技术点

**1. 单事件循环里塞五条流水线，不打架**
小脑（采集/过滤/攒批/审核）、大脑（决策/生成）、行为脑（才艺）、TTS、HTTP 控制台，全部 `create_task` 挂在**同一个 uvicorn 事件循环**上。队列之间靠 `Queue` 传递，每个队列有明确容量（背压）；LLM 抽风只跳过这一批、TTS 抽风只跳过这一句——**单点故障不传染**。

**2. 线程边界只有一处：渲染**
Live2D 必须在主线程吃 60fps，所以渲染独占主线程、只读一块"黑板"；其余全在子线程的事件循环里。跨线程不传对象，只传快照——**渲染循环一秒 60 次，从不等任何人**。

**3. 嘴型不是估的，是算的**
TTS 返回**字级时间戳** → 转音素 → 转嘴型 → 渲染时按 `t` 插值。所以嘴型和声音是同一份时间轴的产物，不是"放音时随机张嘴"。

## 实测数字

| 指标 | 数字 | 说明 |
|---|---|---|
| 首字延迟 | **0.8s**（关思考）vs 6.0s（开思考） | 直播等不起推理，`reasoning_effort="none"` |
| 句间空档 | **1.78s → ≈0** | 合成/播放拆两段，4 句共省 5.4s |
| 弹幕连接稳定性 | **110s 不掉线**（原来约 40s 断一次） | 关掉库自带心跳，改协议级心跳 + 90s 沉默看门狗 |
| 记忆内存占用 | **O(1)** | 从"全量日志读进 dict"换成 SQLite 按需查 |
| 连发 10 条弹幕 | **10 条全过 → 5 批 → 回 5 句** | 限流 5→20 条/10s，攒批 3→2 条 |
| 渲染帧率 | **60fps** | 主线程独占，黑板读快照 |

`Python` · `asyncio`（5 个常驻 Task + 队列背压） · `FastAPI` / `WebSocket` / `uvicorn` · `SQLite`（WAL） · `DeepSeek API`（流式） · `火山 TTS`（字级时间戳） · `Live2D Cubism SDK` · `B 站直播开放协议`（WebSocket + protobuf）

## Web 控制台（FastAPI）

**已全部接好**：跑 `run_vtuber.py` 时，子线程就是"uvicorn 带着五个脑"（同一个事件循环），  
控制台随直播一起起、一起关。

```bash
.venv\Scripts\python.exe run_vtuber.py 30    # 起直播 + 控制台
```

| 地址                           | 是什么                                                      |
| ---------------------------- | -------------------------------------------------------- |
| `http://127.0.0.1:8000`      | **控制台页面**：状态 / 暂停继续 / 说一句 / 才艺 / 换模型 / 换卖货文档 / 弹幕连接 / 用量 |
| `http://127.0.0.1:8000/docs` | 接口文档（FastAPI 自动生成，13 个端点都能点着调）                           |

**原理一句话**：uvicorn 建事件循环，流水线六任务 `create_task` 挂在同一个循环上；  
所有端点读写的就是这些活对象（不收编就得"过桥"，详见工作区《FastAPI 与事件循环 · 学习总结》与《FastAPI 落地文档》）。

**换 Live2D 形象**：把模型文件夹放进 `stage/Resources/v3/` → 控制台里点一下 → 主线程下一帧自己加载  
（画面会顿一下；当前只有 Haru 一个模型，接口已通）。

**换卖货文档**：把 .txt 放进 `卖货文档/` 文件夹 → 控制台里点一下 → 下一轮话术就讲新内容  
（卖货话术和弹幕问产品用的是同一份；重启后记住上次切的那份）。

**排查备忘（实测踩过的坑）**：

- 路径里的中文**必须 percent-encode**：浏览器/网页会自动做；但 python 的 `httpx` 会把含中文的**整条 URL 编错**（表现为 404）——命令行测试先用 `urllib.parse.quote` 编码。
- uvicorn **不要开 `--reload`**（会起两个进程 = 流水线跑两份）。
- 端点里不做同步重活（会卡住整个循环——单循环单线程），重活用 `asyncio.to_thread`。

## 队列规则（谁有资格说话）

两个脑共用一个 TTS 队列，队列项长这样：`(谁说的, 文本)`

| 谁         | 标签     | 抢画面时                  |
| --------- | ------ | --------------------- |
| 行为脑（卖货填充） | `"卖货"` | **丢掉** —— 它是填充，过时了就不说 |
| 大脑（回应弹幕）  | `"回应"` | **保留** —— 弹幕的回应不能被丢   |

**两条规矩都是实测踩出来的：**

| 现象              | 原因                                         | 规则                |
| --------------- | ------------------------------------------ | ----------------- |
| 抢了画面十几秒，中间谁也没说话 | 队列里排着 2 句卖货（一句放 4~6 秒），大脑的话只能排在后面          | **抢画面瞬间清掉排队的卖货**  |
| 大脑的回应一句都听不到     | 弹幕每 3 秒一批，TTS 说一句要 5 秒 —— 下一批抢画面时把上一批回应也丢了 | **只丢"卖货"，保留"回应"** |

> 这一层包在 `pipeline.py` 的 `抢画面时清队列` 里 —— 给行为脑套的壳，行为脑本身不知道队列的存在。

**房间号配在 `.env` 里，代码里不写死**：

```
BILI_ROOM_ID="9369961"     # 空着 = 安静模式（只有卖货，不响应弹幕）
```

打开程序时看终端这几行：

| 打印                                    | 含义                |
| ------------------------------------- | ----------------- |
| `[弹幕] 接入 B站房间 9369961（真弹幕 / 礼物 / 点赞）` | ✅ 读到了房间号          |
| `[弹幕] 已连上 B站房间 9369961 ✓`             | 连接成功（接下来就该有弹幕进来了） |
| `[弹幕] .env 没配 BILI_ROOM_ID → 安静模式`    | 没配房间号             |

**收了哪几类**：弹幕 / 礼物 / 醒目留言 / 点赞，**外加"互动聚合"事件**  
（B站新版协议里的 `DM_INTERACTION`：弹幕聚合 / 礼物聚合 / 点赞聚合 / 关注分享。  
⚠️ 2026-10 实测：B站会把一部分消息**只发聚合事件、不发普通弹幕**——不接这个类型会丢消息），  
其余（进房提示、榜单更新等）忽略。

**两类是聚合过的**（在源层做，防刷屏）：

- **点赞**：攒 6 秒 → 汇成一条「小明、小红 等3人 为主播点赞 ×23」
- **礼物**：连击等 2.5 秒结束 → 合并成一条「辣条 ×5」

**断线自愈**：网络断了它自己重连（2 秒一次），不用重启程序。

**认证必须带的两样（踩了一整天才找到的坑）** —— 缺任何一样，都是"**能连上、能收榜单，但弹幕一条不推**"：

| 字段                | 说明                                                                                        |
| ----------------- | ----------------------------------------------------------------------------------------- |
| **`buvid`（设备指纹）** | 连接前先去拿一份 buvid3 塞进认证包。**空了服务器就不给推弹幕类广播**（只推进房/榜单这类基础广播）—— 这是对照 blivedm 源码找出来的，加上之后弹幕立刻正常  |
| **真实房间号**         | 直播间 URL 里的号可能是**短号**（比如房间 `6` 的真实号是 `7734200`）。token 和认证包都只认真实号 —— 连接前先用 `room_init` 解析一次 |

**连接保活（踩过的大坑）**：库自带的 WebSocket 心跳**不能开** ——  
B站弹幕服务器不回 pong，库等不到就误判"连接死了"自己掐断，  
实测**约 40 秒断一次**（表现就是"弹幕时有时无、很多没受理"）。  
现在保活靠两样：**协议级心跳**（op=2，每 30 秒）+ **沉默看门狗**（90 秒没数据才重连）。  
改完实测 110 秒稳定不掉线。

**单点故障已包住**：LLM 抽风只跳过这一批、火山 TTS 抽风只跳过这一句 ——  
都会在终端打印原因，不会让整个程序停摆（以前一抽风 = 弹幕从此全部没人回）。

### 弹幕的"抓 / 放 / 筛"（三个数字）

| 环节    | 规则（已按实测调过）                                                              | 在哪儿改                                  |
| ----- | ----------------------------------------------------------------------- | ------------------------------------- |
| **筛** | 长度 1~60 字 · 同人同文 10 秒内只留一条 · **每人 20 条/10 秒**（≈每秒 2 条，只有真刷屏才限） · 敏感词送复核 | `cerebellum/filters.py`               |
| **抓** | 够 **2 条**、或距第一条满 **2 秒**，先到先发                                           | `pipeline.py` 的 `batch_n` / `batch_t` |
| **放** | 一批 → 大脑回一次 → TTS 说一次（**排队说，一句要放 5~8 秒**）                                | `pipeline.py`                         |

**调之前踩过的坑**（实测复现："连发 10 句只回 2 句"）：  
限流原来是 5 条/10 秒 —— 连发时一半被砍；攒批是 3 条/3 秒 —— 剩下的又并成 2 批。  
调完：10 条全通过、成 5 批、回 5 句。

**被丢的弹幕会打印出来**（以前是静默丢，最难查）：

```
[小脑] 丢弃 5 条（限流×5）最近一条：「多少钱一包」
```

**每批投递也会打印**（对应"抓了几条、什么时候放"）：

```
[小脑] → 交大脑 2 条 | 三毛：有货吗 / 能开发票吗
```

> 看到丢弃行 = "不是程序没反应，是这条被规则挡了"。嫌太严就改 `filters.py` 里的阈值。

> **回复为什么排队**：一句回复 5~~8 秒，连发 10 条 = 5 批回复 ≈ 30~~40 秒才说完。  
> 这是"说话速度"的物理限制，不是丢消息。

## 弹幕记忆（SQLite = 记忆档案）

**`记忆.db`（SQLite 单文件）是 AI 的"长期记忆"；`弹幕日志.txt` 只是给人看的日志。**

| 项       | 说明                                                        |
| ------- | --------------------------------------------------------- |
| **库文件** | `记忆.db`（单文件，和 `弹幕日志.txt` 并排）                              |
| **写入**  | 弹幕源收到一条就 `INSERT` 一条（和日志**双写**，各记各的）                      |
| **取数**  | 不再"切分"——查询时 `WHERE 用户=? ORDER BY id DESC LIMIT 12`，取几条读几条 |
| **谁用它** | **小脑**：每次投递给大脑前，查一遍"这个人之前在直播间说过什么"                        |
| **去向**  | 拼进大脑的 prompt（`【你对这个人的记忆】`）                                |

**⭐ 为什么从文件换成 SQL（两个真问题）：**

1. **内存**：旧版启动时把整个日志读进 `dict[名字, 50 条]`——     
   **人数 × 50 条全部常驻，人数还没上限**，跑久了把机器吃光。现在内存 = **O(1)**。
2. **截断**：旧版为了省内存，每人只留 50 条（常客说 100 句只记得最后 50 句）。


现在**不截断**——真要给历史设上限，用**按时间清理**（默认 90 天），而不是砍条数。

```
启动时  不载入（库就在那儿）；顺手清一次 90 天前的旧弹幕
运行中  收到即写；投递前按人查最近 12 条
检索    按人查 → [("10-22 13:50", "362L 有货吗"), ...]
```

**效果**：三毛发"再给我来两份"时，大脑看到的是：

```
【你对这个人的记忆】他/她在直播间说过：（10-22 13:50）「362L 有货吗」、（10-22 13:52）「多少钱一盒」
```

> **想清空记忆**：删掉 `记忆.db`（下次启动自动重建）。>   
> **想保留排查证据**：`弹幕日志.txt` 照常追加，但它**不再参与任何逻辑**。

**为什么两个都留**：日志管"发生过什么"（人看、排查"没抓到 vs 抓到没受理"），库管"谁说过什么"（机器查）。职责不同，不合并。

**⭐ 为什么按 `uid` 查、不按昵称：**

| 场景                | 按昵称查                  | 按 uid 查   |
| ----------------- | --------------------- | --------- |
| 两个都叫"小明"          | **记忆串台**，A 说的话被当成 B 的 | 各是各的      |
| 观众改昵称             | 历史**全断**              | 一条不断      |
| 和小脑/UserMemory 对齐 | 一个用名字、一个用 uid，两套主键    | **同一套身份** |

表里同时存 `uid`（主键身份）和 `用户`（展示用，存最近一次看到的昵称）。

**实现位置**：`core/db.py`（`记忆库`：建表/写入/查询/统计/清理）+ `core/danmaku_memory.py`（`弹幕记忆`：对外接口）。

**两个 SQLite 配置**（写在 `记忆库.__init__` 里）：

```python
PRAGMA journal_mode=WAL     # 写只追加日志、不锁读者
PRAGMA synchronous=NORMAL   # 不必每次提交都 fsync —— 最坏丢最后几条，库不会坏
```

不这么做的话，每条弹幕一次 `commit` 都要 fsync；磁盘一忙就是几十毫秒，  
而这行代码跑在**事件循环**里——那几十毫秒里 TTS、收包、大脑全停。
